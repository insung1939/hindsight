8주차(2026-10-21) 팀 발표까지 지켜야 할 것을 한곳에 모았다. 교수님 공지와 중간 발표 피드백은 **원문 그대로** 두고, 그 아래에 우리 해석과 대응을 적는다. 바뀌면 이 문서를 먼저 고친다.

## 1. 교수님 공지 — 8주차 팀 프로젝트 발표 (원문)

> 8주차에는 팀별 프로젝트 발표를 진행합니다. 아래 개발 환경과 필수 내용을 확인하여 프로젝트와 발표를 준비해 주세요.
>
> **1. 개발 환경 및 배포**
> 프로젝트는 수업에서 배운 개발 환경으로 진행해야 합니다.
> - 프론트엔드: React 사용을 기본으로 하되, HTML·CSS·JavaScript를 직접 사용하여 구현하는 것도 가능합니다.
> - 백엔드: FastAPI로 구현합니다.
> - 데이터베이스: PostgreSQL을 사용합니다.
>
> 코드 관리와 배포에는 다음 플랫폼을 사용합니다.
> - GitHub: 소스 코드 및 저장소 관리
> - Vercel: 프론트엔드 배포
> - Render: FastAPI 백엔드 배포
> - Supabase: PostgreSQL 데이터베이스 운영
>
> **2. 데이터 수집 및 활용**
> 외부 API 연동을 통한 오픈 데이터·텍스트 데이터 활용, 크롤링을 통한 비정형 데이터 수집 등 프로젝트 목적에 맞는 방식으로 데이터를 수집하고 활용해야 합니다.
> 사용한 외부 API와 오픈 데이터가 무엇인지 명확히 밝혀야 하며, 서비스에는 수집한 데이터를 분석·정리하여 보여주는 페이지를 기본적으로 포함해야 합니다.
>
> **3. 발표 필수 내용**
> - 서비스 아키텍처: 프론트엔드, 백엔드, 데이터베이스, 외부 API 등의 구성과 연결 관계 및 데이터 흐름
> - 사용 데이터 및 출처: 사용한 외부 API와 오픈 데이터의 명칭, 제공 기관, 출처 URL. 크롤링을 활용한 경우 수집 대상 사이트와 수집 항목 포함
> - 데이터 활용 기획 시나리오: 어떤 사용자의 문제를 해결하기 위해 데이터를 어떻게 활용할 것인지
> - 비즈니스 모델: 서비스의 대상 고객, 제공 가치, 수익 창출 또는 지속 가능한 운영 방안
> - 주요 페이지 및 기능: 구현했거나 구현할 예정인 페이지의 구성과 각 페이지에서 제공할 기능
> - 데이터 분석·정리 결과: 수집한 데이터를 분석·정리한 페이지와 주요 결과 소개
>
> **4. 발표 자료에 반드시 포함할 주소 및 문서**
> - GitHub 저장소 주소: 프로젝트 소스 코드를 확인할 수 있는 주소
> - 서비스 웹 주소: 배포된 서비스에 접속할 수 있는 프론트엔드 주소
> - Swagger UI 주소: 배포된 FastAPI 백엔드의 API를 확인하고 테스트할 수 있는 주소
> - API 설명 문서: 구현한 주요 API의 기능, 요청 방식, 입력값 및 응답 형식 등
> - DB 테이블 문서: 테이블 구성, 주요 컬럼, 기본키·외래키 및 테이블 간 관계 등
>
> 발표 자료에서 위 주소와 문서를 바로 확인할 수 있도록 링크 또는 관련 내용을 포함해 주세요.
>
> **5. 구현 및 평가 안내**
> 실제 구현 과정에서 에이전트 코딩을 활용해도 됩니다. 발표에서는 프로젝트의 기획과 구조, 데이터 활용 방식, 주요 기능을 설명해 주세요.
> 프론트엔드는 평가에서 제외합니다.

## 2. 중간 발표(5주차, 2026-09-30) 피드백 (원문)

> UI를 강화하지 말고 데이터를 수집해서 쓰는 것. 외부의 자원을 잘 활용해야 한다.
> 데이터와 API 호출 중심으로 가자. (어떤 소스에서 데이터를 가져와서 어떻게 가공해서 가져올 것인지가 중심이 되어야 한다.)
> 필요한 데이터가 무엇인지, 그리고 그것으로 무엇을 하고 어떠한 가치를 제공하는지가 평가의 키 포인트이다.

### 우리 해석
- **평가의 축은 세 가지**: ① 어떤 외부 소스를 ② 어떻게 가공해서 ③ 무슨 가치를 만드는가. 화면은 그 결과를 보여주는 창일 뿐이다.
- 발표의 절반 이상을 **데이터 파이프라인(소스 → 수집 → 매칭 → 계산 → 결과)**에 쓴다. 각 단계마다 실제 건수를 붙인다.
- 서비스 안의 **데이터 페이지**를 "출처 표"에서 끝내지 않고, 수집 건수·매칭 성공률·못 잡은 제목·배치 실행 기록까지 보여주는 **파이프라인 대시보드**로 키운다.
- 외부 자원은 많을수록 좋다. 단, 각 소스가 **어떤 질문에 답하는지**가 분명해야 한다. (후보는 4장)

## 3. 발표 자료·서비스 디자인 원칙

- **가독성 우선.** 강의실 조명 때문에 어두운 바탕의 글자가 안 보였다는 팀원 메모 반영. 밝은 바탕을 기본으로 하되 흰색 강제는 아님(2026-10-07 조인성). 본문 명암비 4.5:1 이상, 큰 글씨. 톤은 `insung_introduction`(Pretendard, 남색·파란 포인트, 절제된 인터랙션)을 따른다. 프론트는 평가 제외이므로 공은 데이터 쪽에 들인다.
- 큰 글씨, 한 화면에 한 메시지. 표와 숫자는 크게, 장식은 없음.
- 발표는 별도 슬라이드 없이 **웹 발표 페이지**로 한다(교안 안내). 서비스(`apps/web`)와 발표 페이지(`apps/team-page`)는 따로 만든다.
- 채널은 실명 표시·채널별 성적 공개(2026-10-07 결정, 학습용 고지 고정), 종목 추천 문구 금지, 표본 수 항상 표시.

## 4. 서비스 정의 (팀 합의본)

> **유튜버 영상 이후의 주가흐름 분석**
> - 무엇: 주식·코인 유튜브 채널이 제목에서 언급한 종목이 그 뒤 어떻게 됐는지 보여주는 서비스.
> - 화면: ① 이번 주 언급 급증 종목 ② 언급 뒤 5·20·60일 수익률 통계(전체·채널 집계) ③ 종목 하나의 언급 시점과 주가를 한 그래프에.
> - 데이터: YouTube API(제목·게시일) + 업비트 API + 주가. 범위는 채널 20개, 최근 1년. 하루 영상 30~60개.
> - 역할 4~5개: 유튜브 수집 / 종목 매칭 / 주가 수집 / 통계 계산 / 화면.
> - 왜 좋나: 화제성이 크고 발표가 재밌다. 제목에서 종목명 뽑는 작업이 핵심. 채널 실명 랭킹은 논란 소지가 있어 집계 위주.
> - 예: "삼전 급등 예정" → 과연 5·20일 기준 올랐을까? y/n

데이터는 더 추가해도 된다(평가 비중이 데이터에 있으므로). 추가 후보와 우선순위는 `docs/checklist.md` 3장.

## 6. 비밀값 규칙

- API 키·DB 주소는 **`.env`(로컬)와 Render·Vercel·GitHub Secrets(배포)에만** 둔다. 문서·코드·커밋·채팅에 적지 않는다.
- YouTube 키: `services/youtube/.env` 의 `YOUTUBE_API_KEY`. (`.gitignore` 로 제외됨)
- 발급이 필요한 키: `DART_KEY`(opendart.fss.or.kr, 즉시), `DATA_GO_KR_KEY`(data.go.kr, 승인 1~2일). 네이버 뉴스 검색 API 는 2026-10-07 제외(과금 우려·소급 불가).
- 키 목록과 자리는 저장소 루트 `.env.example` 이 기준.
